# Playwright Network Interception

## 1. Introduction

Playwright provides powerful APIs for monitoring, intercepting, modifying, mocking, and controlling network traffic generated by a web application.

Network interception is useful for:

* Monitoring API requests
* Validating API responses
* Mocking backend services
* Testing error scenarios
* Modifying request headers
* Modifying request payloads
* Blocking unwanted resources
* Simulating slow APIs
* Testing applications when backend services are unavailable
* Creating stable and faster UI tests

---

## 2. Network Concepts

A typical browser interaction looks like:

```text
Test
  |
  v
Browser
  |
  v
Web Application
  |
  v
API Request
  |
  v
Backend Server
  |
  v
API Response
  |
  v
Web Application
```

Playwright allows us to observe or intercept the request between the browser and backend.

```text
Browser
   |
   |---- Request ---->
   |
   |   Playwright
   |   Intercepts
   |
   |---- Modified Request ---->
   |
Backend
```

# 3. Monitoring Requests

Playwright provides the `request` event.

```javascript
page.on('request', request => {
    console.log('Request:', request.url());
});
```

Example:

```javascript
import { test } from '@playwright/test';

test('Monitor requests', async ({ page }) => {

    page.on('request', request => {
        console.log(
            request.method(),
            request.url()
        );
    });

    await page.goto('https://example.com');

});
```

# 14. Route Interception

The most important network interception API is:

```javascript
page.route()
```

Basic syntax:

```javascript
await page.route('**/api/users', async route => {

    // Intercept request

});
```

# 15. `route.continue()`

`route.continue()` allows the request to continue to the real backend.

```javascript
await page.route('**/api/users', async route => {
    await route.continue();
});
```

This is useful when you want to inspect or modify a request but still send it to the server.

---

# 16. Modify Request Headers

Example:

```javascript
await page.route('**/api/users', async route => {

    const headers = {
        ...route.request().headers(),
        'x-test-environment': 'automation'
    };

    await route.continue({
        headers
    });

});
```

The original request headers are preserved and the new header is added.

---

# 17. Modify Authorization Header

This can be useful for test environments.

# 20. `route.abort()`

`route.abort()` prevents the request from reaching the server.

```javascript
await page.route('**/analytics/**', async route => {
    await route.abort();
});
```

Useful for:

* Blocking analytics
* Blocking advertisements
* Blocking unwanted resources
* Simulating network failures

---

# 21. Abort Specific Resource Types

```javascript
await page.route('**/*', async route => {

    const type = route.request().resourceType();

    if (type === 'image') {
        await route.abort();
    } else {
        await route.continue();
    }

});
```

Resource types include:

```text
document
stylesheet
image
media
font
script
texttrack
xhr
fetch
manifest
websocket
other
```

# 22. `route.fulfill()`

`route.fulfill()` allows us to provide our own response.

Example:

```javascript
await page.route('**/api/users', async route => {

    await route.fulfill({
        status: 200,
        contentType: 'application/json',
        body: JSON.stringify({
            users: [
                {
                    id: 1,
                    name: 'John'
                }
            ]
        })
    });

});
```

The real backend is not called.

# 30. Modify Existing Response

Instead of creating a completely new response, use:

```javascript
route.fetch()
```

Example:

```javascript
await page.route('**/api/users', async route => {

    const response = await route.fetch();

    const json = await response.json();

    json.users.push({
        id: 999,
        name: 'Mock User'
    });

    await route.fulfill({
        response,
        json
    });

});
```

This approach is useful when you want the real backend response but need to modify it.

# 50. Global Network Logging

A reusable helper can log network traffic.

```javascript
export function enableNetworkLogging(page) {

    page.on('request', request => {

        console.log(
            `[REQUEST] ${request.method()} ${request.url()}`
        );

    });

    page.on('response', response => {

        console.log(
            `[RESPONSE] ${response.status()} ${response.url()}`
        );

    });

    page.on('requestfailed', request => {

        console.log(
            `[FAILED] ${request.url()}`
        );

    });
}
```

Usage:

```javascript
import { enableNetworkLogging } from './utils/network.js';

test('Network logging', async ({ page }) => {

    enableNetworkLogging(page);

    await page.goto('https://example.com');

});
```

# 61. Network Mocking vs API Testing

Network mocking:

```text
UI
 |
 v
Playwright
 |
 X
Real API
```

API testing:

```text
Test
 |
 v
API
 |
 v
Backend
```

Network mocking validates how the UI behaves when different API responses occur.

API testing validates the API itself.

Both are useful in an automation framework.

# 62. Network Interception Best Practices

### 1. Mock only what is necessary

Avoid mocking the entire application backend unless required.

### 2. Use realistic test data

Bad:

```javascript
{
    users: []
}
```

when the UI expects many fields.

Better:

```javascript
{
    id: 1001,
    name: 'Automation User',
    email: 'automation@example.com',
    status: 'ACTIVE'
}
```

### 3. Keep mocks reusable

Create utility functions or fixtures.

### 4. Test both positive and negative responses

For example:

```text
200
201
400
401
403
404
500
```

### 5. Do not overuse network mocking

Excessive mocking can hide real integration problems.

### 6. Keep API contracts realistic

The mocked response should match the real backend structure.

# 64. Common Interview Question

### What is the difference between `route.continue()`, `route.fulfill()` and `route.abort()`?

| Method             | Purpose                          |
| ------------------ | -------------------------------- |
| `route.continue()` | Sends request to the real server |
| `route.fulfill()`  | Provides a custom/mock response  |
| `route.abort()`    | Blocks the request               |

Example:

```javascript
await route.continue();
```

```javascript
await route.fulfill({
    status: 200,
    body: 'Mock response'
});
```

# 74. Common Interview Question

### What is the difference between `page.on('request')` and `page.route()`?

`page.on('request')` is primarily for observing requests.

```javascript
page.on('request', request => {
    console.log(request.url());
});
```

`page.route()` allows you to intercept and control requests.

```javascript
await page.route('**/api/**', async route => {
    await route.continue();
});
```

# 78. Recommended Network Testing Strategy

For a senior-level automation framework:

```text
UI Test
   |
   +---- Real API
   |       |
   |       +---- Integration validation
   |
   +---- Mock API
           |
           +---- Positive scenarios
           +---- Error scenarios
           +---- Empty data
           +---- Slow response
           +---- Retry
           +---- Unauthorized
           +---- Forbidden
```

Use real APIs when validating integration.

Use mocks when testing UI behavior against conditions that are difficult, slow, unstable, or expensive to reproduce with the real backend.
